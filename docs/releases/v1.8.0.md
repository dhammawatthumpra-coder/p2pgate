# p2pgate v1.8.0

SOCKS5 gateway: route browser or app traffic through the Server to destinations
you explicitly allow. No TUN, no root, works on Termux.

## Server config

```json
"socks": {
  "enabled": true,
  "allow": ["127.0.0.1:3000", "192.168.1.0/24:8080", "10.0.0.0/8:*"]
}
```

- off by default; `socks.enabled` requires at least one allow entry
- entries are IPv4/CIDR plus a port (`*` = any port)
- hostnames are resolved on the Server and **every** resolved IP is checked
  against the allowlist, so DNS rebinding cannot escape it

## Client

```sh
p2pgate connect -s <secret> -p <password> --socks5 1080
# then point the browser/app at SOCKS5 127.0.0.1:1080
```

- `--socks5` is saved as `socks5Port` in `client.json`
- `--socks5` and `--target` are mutually exclusive
- the banner reports `SOCKS5: 127.0.0.1:<port>`

## What it does and does not do

| Supported | Not supported (v1.8) |
|---|---|
| TCP `CONNECT` | `UDP ASSOCIATE`, `BIND` |
| IPv4 destinations | IPv6 destinations |
| Server-side DNS with IP allowlist | client-side DNS policy |
| Per-connection tunnel | multiplexed tunnel |

## Security

- the allowlist is enforced on the Server; the Client cannot widen it
- a SOCKS success reply is sent only after the tunnel is authenticated, so a
  denied destination never looks like an open proxy
- denied requests log `SOCKS DENIED destination=<host>:<port>` and do not count
  as failed authentication attempts
- `0.0.0.0/0` is possible but turns the Server into an open gateway — do not do
  that on a machine you do not control

## Testing tip

`curl` may bypass the proxy when `NO_PROXY` contains `127.0.0.1`:

```sh
curl --noproxy "" --socks5-hostname 127.0.0.1:1080 http://192.168.1.50:8080/
```

## Compatibility

- drop-in replacement for v1.7.0
- configs without `socks` behave exactly as before
- protocol version unchanged; the SOCKS field is an optional addition

## Tests

`npm test` → 45 checks (4 new):

- SOCKS5 CONNECT reaches an allowlisted destination
- SOCKS5 resolves a hostname and checks the resolved IP
- SOCKS5 denies a destination outside the allowlist
- SOCKS5 is refused when the server has it disabled

Manual verification on Windows: allowed destination returned `SOCKS-OK`,
denied destination failed with a SOCKS error while the Server logged
`SOCKS DENIED`.
