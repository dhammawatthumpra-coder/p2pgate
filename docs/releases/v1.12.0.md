# p2pgate v1.12.0

Multiplexing: one authenticated carrier, many channels. Opt-in via `--mux`.

## Why

`p2pgate ping` on a real link showed:

```text
connect 2130/2263/2424 ms   auth 26/28/32 ms
```

Every local connection paid a full DHT lookup. A page through `--socks5` opens
20–40 connections, so the page waited on 20–40 lookups.

## What changed

```sh
p2pgate connect -s <secret> -p <password> --socks5 1080 --mux
p2pgate client --config client.json --mux
```

- one carrier is authenticated once, then channels are opened per request
- channels share the carrier's flow control (256 KiB per direction, 16 KiB frames)
- up to **128 channels** per carrier
- carrier idle timeout 5 minutes, keepalive every 30 s
- channel open failure (unknown target, SOCKS deny) returns the same error codes
  as before and the client falls back to a dedicated stream

## Important limitation

A **trusted (fast-path)** device cannot negotiate mux: the server answers
`FASTPATH_READY` before reading the proof, then pipes to the target. With
`--mux` such a session logs a warning and falls back to one stream per
connection — no breakage, just no speed-up.

To use mux on a device, register its key with the `scram` profile (challenged)
or use password mode.

## Security

- `OPEN` carries a target **name** or a SOCKS destination checked against
  `socks.allow`
- no raw `host:port` for TCP targets
- unknown channels are `RESET`; per-channel buffer cap 64 KiB
- carrier authentication is the normal SCRAM handshake

## Visibility

- `status --json` lists the mux session as a `kind: "mux"` record under `traffic.active`
  (carrier/channel counts were added in 1.12.1)
- channel activity is not written to the audit log (volume); use status/logs
- `MUX carrier established`, `MUX OPEN`, `MUX SESSION closed` log lines

## Tests

`npm test` → 60 checks (3 new):

- mux framing round-trips a frame
- mux carrier serves a challenged session
- mux falls back on a fast-path session

Manual: two SOCKS requests through one carrier returned `BB` with the server
logging two `MUX OPEN` lines under a single `MUX SESSION`; a denied destination
still returned a SOCKS failure.

## Compatibility

- opt-in; existing behaviour unchanged
- 1.12 client + older server: mux is refused, client falls back
- no config migration
