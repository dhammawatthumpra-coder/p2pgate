# p2pgate v1.13.2

Hotfix for a fast-path regression introduced in 1.13.0: the first bytes a client
sends could be dropped, which broke `ssh` through a non-mux tunnel.

## What happened

1.13.0 added a bounded peek on the fast path: the server advertises mux, waits up to
200 ms for an upgrade line, then forwards. The peek returned the bytes **after** the
newline it parsed and discarded the line itself. For a client that does not use mux,
that line is real payload — for SSH it is the banner:

```text
SSH-2.0-OpenSSH_9.5\r\n     <- eaten by the peek
```

The ssh client then saw a desynchronised stream:

```text
Bad packet length 1231976033.
ssh_dispatch_run_fatal: ... message authentication code incorrect
```

Affected: trusted (fast-path) sessions **without** `--mux`. Sessions that upgrade to
mux never reach that branch, and challenged sessions never had a peek.

## Fix

`peekControlLine()` now also returns `raw`: every byte it read, including the line and
its newline. When the line is not a valid mux upgrade the server forwards `raw`
instead of `leftover`, so nothing is lost. The mux upgrade path still uses the bytes
after the line, which is what the carrier wants.

A new self-test writes a line immediately after connecting (exactly how SSH behaves,
inside the peek window). It fails on 1.13.0/1.13.1 and passes after the fix:

```text
✅ fast-path peek forwards an immediate line payload (SSH banner)
```

## Upgrade

```sh
npm i -g p2pgate@1.13.2
```

Then restart the server and the client. Until you upgrade, running the client with
`--mux` avoids the bug (that path never peeks).

`npm test` → **73 checks**.
