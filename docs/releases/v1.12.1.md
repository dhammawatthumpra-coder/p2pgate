# p2pgate v1.12.1

Correctness release for mux **and** for the normal tunnel path. No protocol change.

## The bug worth reading

While stress-testing 1.12.0 with large transfers, an 8 MiB file came out **short**
with no error. Two independent causes, both in teardown:

1. **Dedicated streams truncated on graceful close.** When one side finished, the
   other side called `destroy()` on the peer socket/stream in the same tick, so the
   last write still sitting in the buffer was discarded. Any `scp`, `rsync` or file
   download could lose its tail while looking successful.
2. **mux had no backpressure and no real half-close.** A client kept reading from
   the local socket while the channel queue was full (unbounded memory), and it
   sent `CLOSE` immediately after its own write side ended, which closed the channel
   both ways — the reply still in flight was dropped.

Both are fixed. `CLOSE` is now a FIN: a channel stays open until **both** sides have
finished sending.

## What changed

| Area | Before | Now |
|---|---|---|
| client → carrier | queue unbounded, write ignored | `write()` returns `false`, emits `drain`, socket pauses |
| channel end | `CLOSE` closed both directions | half-close; channel closes when both FINs are seen |
| server → target | 64 KiB overflow → immediate `RESET` | pause socket at 64 KiB, `RESET` only above 1 MiB |
| dedicated stream teardown | `destroy()` on first `close` | flush with `end()`, release after both sides close |
| concurrent first connections | one carrier per connection (DHT lookup each) | single in-flight carrier promise |
| server limits | 128 channels per carrier only | also 64 carriers and 512 channels per server |

`MUX_BUSY` is returned when a limit is reached; existing error codes are unchanged.

## Visibility

```text
MUX SESSION closed client=… channels=3 in=8388608 out=8388608
```

`status --json` now reports real carrier/channel counts:

```json
"traffic": { "mux": { "carriers": 1, "channels": 2 }, "active": [ … ] }
```

## Verified on one machine (Windows, Node 24)

| Test | Result |
|---|---|
| mux, 8 MiB and 32 MiB upload + echo | SHA-256 match |
| mux, 16 MiB download (target sends first) | SHA-256 match |
| mux, 8 parallel channels × 4 MiB, one carrier | all channels match |
| mux through SOCKS5, 8 MiB download (`--socks5 --mux`) | SHA-256 match, ~3.5 MB/s |
| abort mid-transfer, then reconnect | probe payload intact |
| dedicated stream, 16 MiB × 3 runs | match |
| `npm test` | **66 checks passed** |

Peak RSS for the 32 MiB mux test was ~149 MB (payload + echo copy in the test
process), not a leak indicator.

## Upgrading

Drop-in. `npm i -g p2pgate@1.12.1`. Old servers can still serve 1.12.1 clients
without mux; mux itself is unchanged on the wire, only teardown behaviour differs.

If you transferred large files through 1.11.x or 1.12.0, re-check their checksums —
tails may have been lost silently.
