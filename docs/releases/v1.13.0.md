# p2pgate v1.13.0

Multiplexing now works for **trusted devices** too — the case most people use.

## Why this release exists

1.12 shipped `--mux`, but only on a *challenged* session. A trusted device gets
`FASTPATH_READY` and the server starts piping before it reads any proof, so mux had
nowhere to negotiate. In practice that meant:

```text
MUX unavailable (fast-path or older server); using dedicated streams
```

— exactly the users who run one or two sessions from a registered device.

## How it works

```text
server → {"v":3,"status":"FASTPATH_READY","mux":{"version":1,"maxChannels":128}}
client → {"v":3,"mux":{"version":1}}          (only when --mux is on)
server → {"v":3,"mux":{"version":1,"maxChannels":128}}   then a mux session
```

The server peeks for that one line for at most **200 ms / 512 bytes**. Anything else —
an old client's first payload bytes, a protocol that starts with `{` — is forwarded to
the target byte-for-byte, so nothing changes for clients that do not ask.

```sh
p2pgate connect -s <secret> -p <password> --socks5 1080 --mux   # password mode
p2pgate client --config client.json --mux                       # trusted device
```

## Compatibility

| client | server | result |
|---|---|---|
| 1.12.x | 1.12.x | unchanged |
| 1.12.x | 1.13.x | payload forwarded, mux not used |
| 1.13.x | 1.12.x | no capability, quiet fallback |
| 1.13.x | 1.13.x | mux on the fast path |

`AUTH_VERSION` stays `3`; the capability is an additive field, and the challenged
flow is untouched.

## Config

| key | default | meaning |
|---|---|---|
| `mux` | `true` | advertise mux on the fast path |
| `muxPeekMs` | `200` | peek window; `0` restores exact 1.12 behaviour |

Rollback is config-only (`mux: false`) or client-side (`--mux` off).

## Costs

- mux clients pay no extra latency — the upgrade is sent immediately after
  `FASTPATH_READY`.
- non-mux clients that speak first (SSH, HTTP) pay nothing.
- the only added delay is a server-first protocol with an idle client: at most 200 ms,
  once per connection, and it can be disabled.

## Security

- reachable only on already trusted devices; no new authentication path
- channels still resolve targets through `resolveTarget` / `resolveSocksTarget`
- peek is bounded (512 B, 200 ms) and does not consume the auth concurrency guard
- carrier/channel caps from 1.12.1 unchanged (64 / 512)

## Tests

`npm test` → **71 checks**, including:

- `peekControlLine` line + trailing bytes, newline-less payload, byte-limit cut-off
- mux works on a fast-path session
- payload beginning with `{` is forwarded intact
- server with `mux: false` advertises nothing and the client falls back
