# p2pgate v1.13.3

`--target` now works on the fast path (trusted devices). Before this release it was
silently ignored and the server forwarded to `defaultTarget`.

## The bug

A client sends the requested target inside the SCRAM proof message. A trusted device
never sends a proof — the server answers `FASTPATH_READY` and pipes. So:

```text
client: p2pgate client --target mcp --port 18787
client log: TUNNEL established slot=498598
server log: FASTPATH client=3d8f1d…
            FORWARD  client=3d8f1d… target=default -> 127.0.0.1:8022
result:     HTTP on 18787 gets the SSH banner
```

It only affected fast-path sessions; challenged sessions always routed correctly.

## Fix

The server now advertises the capability in the ready frame and the client states the
target during the same 200 ms peek that mux already used:

```text
server → {"v":3,"status":"FASTPATH_READY","mux":{…},"target":true}
client → {"v":3,"target":"mcp"}
server → {"v":3,"target":{"name":"mcp","host":"127.0.0.1","port":8787}}
```

- zero extra round trips: the line is sent immediately after the ready frame
- the client still sends a **name**, never `host:port`; the server owns the mapping
  (no new authority, and per-target `allow` still applies)
- unknown or forbidden target → the server answers with an error and closes
- an older server does not advertise `target`, and the client now fails loudly with
  `TARGET_UNSUPPORTED` instead of quietly using `defaultTarget`

## Compatibility

| client | server | `--target` on fast path |
|---|---|---|
| ≤1.13.2 | ≤1.13.2 | ignored (the bug) |
| 1.13.3 | ≤1.13.2 | rejected with `TARGET_UNSUPPORTED` |
| 1.13.3 | 1.13.3 | routed correctly |
| ≤1.13.2 | 1.13.3 | unchanged (client never asks) |

`muxPeekMs: 0` disables the peek, so both mux and fast-path target requests are
unavailable there by design.

## Tests

`npm test` → **76 checks**, including:

- `fast-path --target reaches the requested target`
- `fast-path rejects an unknown target instead of using the default`

Both run against two servers with different banners, so a regression is unambiguous.
